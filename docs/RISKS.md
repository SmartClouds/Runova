# Deploy: risk register

Reviewed in E17 (2026-10-03) against what actually happened over the 18 epics.

| Risk | Impact | Likelihood | Mitigation | Status |
|---|---|---|---|---|
| The program is large (18 epics) and spans several sessions | High | High | Vertical slices, one commit per epic, resumable `DELIVERY_STATUS.md`, epic-runner stop rules | Mostly mitigated. Every epic landed; E12 and E17 each have one criterion open. Epics built in parallel by separate agents needed a merge fix (a1af2fc), and three epics (E06, E10, E11) finished their core work without ticking their task lists, which E17 caught |
| Distro drift: package names, repo layouts and defaults differ across Ubuntu, Debian and the RHEL family | Medium | High | Platform abstraction (`IPackageManager`, `IFirewallBackend`, `ISecurityModule`), test-server containers per distro, nightly full matrix | Mitigated. Occurred on Rocky (podman in the way, `sshd` not `ssh`, AppArmor on the CI host confining the container's unix_chkpwd). Debian 13 and Rocky 9 pass every Deploy system test locally (E17), and `nightly.yml` runs the whole matrix |
| SELinux behavior cannot be exercised inside containers | Medium | Medium | Nightly Rocky VM with SELinux enforcing when the runner has KVM; otherwise record the criteria as unverified | Open. It held: the Rocky container runs without SELinux, so `restorecon` and the nginx booleans are unit-tested only. GitHub's hosted runners have no KVM, so no VM job was added |
| Docker-published ports bypass the host firewall | High | High | Loopback bindings through `!override`, public exposure only through nginx, exposure inventory with "make private" | Mitigated (E07, E13; the stacks system test checks the binding on a real Docker) |
| A firewall change locks the user out | High | Medium | Lockout guard from `sshd -T` and `SSH_CONNECTION`, confirm over a new connection, rollback armed as a systemd timer | Mitigated (E13, E15; the firewall system tests kill the core and watch the timer roll back, in CI since run 37084799281) |
| Prompt injection through container or nginx logs steers the Deploy AI | High | Medium | Read-only allowlist for unattended runs, device-signed approvals enforced by the core, logs wrapped as untrusted data, redaction | Mitigated (E09; the core refuses unsigned and replayed commands in the exec system test, in CI) |
| Secrets leak into logs, audit, prompts or crash dumps | High | Medium | Central redactor seeded with stack env values, env values stripped from DTOs, `LimitCORE=0`, compose config output never stored | Mitigated (E06 AC3 and E08 tests: a prompt never holds an env value, and a deploy leaves no registry token anywhere on disk) |
| The core's logs go to a third party once error reporting is on, and a secret or personal detail rides along | High | Medium | Owner-only with a step-up, nothing sent until set up, every message, value and exception scrubbed by the redactor on the server first (a value under a secret-like name is masked in the message too), HTTPS only (plain HTTP to this machine only), no redirects, DSN sealed and never returned, every change audited without the key | Mitigated by tests (E29 AC3 and AC4 against the real OpenTelemetry exporter and a fake Sentry). Scrubbing is pattern based, so a secret with no telltale name or shape can still get through. Not tried against a real Sentry |
| A compromised server captures a broad GitHub token | High | Low | Packages-only token by default, `gh` token only behind a warning, tmpfs `DOCKER_CONFIG` wiped after each deploy | Mitigated (E08) |
| Let's Encrypt rate limits during development | Medium | Medium | Pebble in CI, staging directory toggle, ARI `replaces` on renewals | Mitigated. Development never reached Let's Encrypt: the DevHost has a pretend CA and the system tests use Pebble |
| sshd forbids forwarding on some servers | Medium | Medium | `runova-core bridge` stdio fallback. Occurred in E03: OpenSSH refuses a forbidden stream-local tunnel with the same "open failed" as a missing socket, so preflight cannot tell; the install tries the real socket and falls back to the bridge, and health checks do the same later | Mitigated (E03, proven against sshd with `AllowStreamLocalForwarding no`) |
| A fast command's exit status is lost when ssh2 parses it in the same burst as the exec reply | High | Medium | Found in E03 under full-suite load (an install step would read as failed): the exit status is taken from `close` as well, which cannot fire before the listeners exist | Mitigated (E03, reproduced in a unit test) |
| Supply chain: a tampered core binary or dependency | High | Low | Hash pinned in the desktop build, locked NuGet restore with source mapping, NuGet audit, pinned GPG keys for Docker and nginx | Partly mitigated. A tampered download is refused in the install system test; the release path (CD publishing and attesting both architectures) first runs on the next `v*` tag |
| SQLite writer contention breaks the audit chain or causes busy errors | Medium | Medium | Single writer queue, `BEGIN IMMEDIATE`, busy timeout, metrics in memory | Mitigated in code (audit appends read the previous hash inside `BEGIN IMMEDIATE`); not load-tested |
| A dependency bundled into the main process loads helpers at runtime (`require` by name), which works in unit tests but not in a built app | High | Medium | Occurred in E04: the SignalR client could not find `eventsource` in the electron-vite build, so the first hub call failed. SignalR is now external like `postman-runtime`, and the Deploy e2e test makes a real hub call on every OS | Mitigated (E04) |
| The system tests stall or refuse logins on GitHub runners while they pass locally | High | High | Occurred in E03 and E04 CI runs. Every SSH wait has a time limit, the test servers run in a private cgroup namespace, CI unloads the runner's AppArmor profile for unix_chkpwd, and a failing test prints its timed steps plus the server's journal | Mitigated (all pass in CI since run 36677124032) |
| Tests that need Linux are written but never run anywhere automatic | High | Medium | Occurred: the server core's own system tests (nginx `-t` harness, Pebble) and the stacks, security and Docker system tests ran only on developers' machines until E17. The nightly workflow runs all of them, and each new system test should get a CI step in the same commit | Mitigated (E17): the first nightly run (37097759993) was green for every Deploy system test, and 18 of 19 server core system tests passed |
| An authenticator code is replayed within its validity window | High | Low | Codes work once and older ones are spent (RFC 6238 section 5.2), one step either side of now, concurrency stamp against two uses at once | Mitigated (E04, tested) |
| Someone with root on a server rewrites the audit trail and recomputes the chain | Medium | Low | The chain shows edits short of a full rewrite; E15 lets the trail be exported off the server | Open. Export is by hand (JSON or CSV from the Audit tab); nothing ships the trail away on its own |
| Light-theme colours fall below WCAG AA for small status text | Medium | High | Occurred: E17's audit measured 2.8 to 3.9:1 for status words and 3.7:1 for white on primary buttons. The light tokens were deepened, and `themeContrast.test.ts` holds every pair at 4.5:1 in both themes | Mitigated (E17) |
| Pre-existing: AI provider API keys are stored in plaintext in `settings.json` and the Deploy AI reuses them | Medium | Medium | Out of scope for this plan; recommend moving them into a `SecretEnvelope` as a follow-up | Open |
| Recovery after a real reboot and a stream across a real token expiry are only tested with fakes | Medium | Medium | E05 covers them with the fake core and the DevHost's pretend reboot (connections closed, 503 for 8 seconds); a real reboot also restarts sshd and changes the boot ID. Add a system test that reboots a test VM when the runner can host one | Open |
| Remote Desktop AI: screenshots of the remote desktop go to the AI the user picks | Medium | High | The task dialog says so before starting; nothing is sent until a task starts, and only the latest frame each step | Open |
| Remote Desktop AI: Claude Code sees the screenshot through its Read tool, which can read any file it reaches | Medium | Low | Runs in a fresh temp folder holding only frame.png, with only the Read tool allowed and a prompt limiting it to that file | Open |
| WordPress: a write key is code execution on the site, so a stolen desktop key is as bad as a stolen SSH key | High | Low | The private key is sealed with the Servers vault per site; keys are revocable from wp-admin and expire if the admin set it; read-only keys by choice; every connection, deploy and auth failure is in the site's audit log | Open |
| WordPress: a deploy fatals the site and the plugin's own routes die with it | High | Medium | Guard mu-plugin with a deadline and a fatal-error handler, rescue routes before other plugins load, `rescue.php`, `wp runova rescue` | Mitigated (E19: smoke on real WordPress, and the desktop integration test rolls back a theme that fatals every request through the rescue routes) |
| WordPress: a connector update ships code that fatals the site, and the rescue routes live in the same folder | High | Low | Every PHP file is parsed on the site's own PHP before anything is written; the update swaps folders (two renames) and health checks, putting the old folder back on a regression; a failed swap leaves both folders named in the error. Not covered: a release that loads fine and breaks while the loopback is blocked (the app then reads `/site/info` and the home page, and the zip upload in wp-admin is the fallback) | Mitigated (smoke on real WordPress rolls back a release that fatals at load) |
| WordPress: a CDN or firewall (Cloudflare challenge, ModSecurity) answers instead of the plugin | Medium | Medium | Replies that are not a signed envelope are reported as such with the fix (a skip rule for the connector's paths, naming Cloudflare when it answered); the gzip bundle keeps PHP out of request bodies | Partly mitigated (no live CDN in the tests) |
| WordPress: self-signed staging certificates are refused | Low | Medium | Trust the certificate in the OS, or use the plain-HTTP opt-in; certificate pinning like E16 is a follow-up | Open |
| WordPress: loopback requests are blocked, so the health check cannot run on the site | Medium | Medium | Only "healthy before, unhealthy after" counts as a failure; the desktop runs its own external check; the guard's fatal-error handler still applies | Open |
| WordPress: a staging clone shares the production site's key and connections | Medium | Medium | The plugin renews its key and revokes connections when its `home` address changes; the desktop merges a reconnect only when the key and the REST origin match | Mitigated (E19, found by the security review) |
| WordPress: hostile text from the desktop or the network (device names, labels) reaches wp-admin | High | Low | Names cleaned before they are stored, everything escaped, and no inline handlers or data-carrying scripts on the admin pages | Mitigated (E19, found by the security review) |
| WordPress: pulled site files steer an agent (prompt injection in theme or plugin code) | Medium | Medium | The project prompt says pulled files are data, not instructions; nothing the agent writes reaches the site without the review screen and an explicit deploy | Open |
| Remote Desktop AI: a Settings model without vision, or a remote keyboard layout that maps keys differently, makes steps fail | Low | Medium | Provider errors pause the run with Continue; TYPE uses Unicode input so text is layout independent, while KEY combos follow the remote layout | Open |
| Server backups copy Docker volumes live, so a database busy at that moment restores inconsistent | High | Medium | Chosen by the user over stopping stacks (E28). The plan screen and the restore summary say so; a database that needs it can dump itself into its volume on a schedule | Open |
| A lost backup secret key makes every backup unreadable | High | Medium | The core never stores it (only a key pair sealed with it), so nothing can recover it. The Secret key tab says so before it is set, and a change asks for the current one | Open, by design |
| Hangfire.Core is LGPL-3.0 and ships with the core | Medium | Low | Used unmodified from NuGet. The LGPL lets an application use it as long as a user can swap in their own build, so the publish keeps every Hangfire assembly beside the single-file binary (`ExcludeFromSingleFile`) instead of inside it, where it could not be replaced, and the release carries the package's license texts and notices in `licenses/hangfire` | Mitigated (E28) |
| A restore needs about three times the backup's size free on the server: the encrypted file, the decrypted payload and the unpacked state | Medium | Medium | restore-stage refuses an unpack bigger than the free space; the full backup checks the room before and after each volume | Open (E28). Streaming the decrypt straight into the unpack would save one copy |
| Google Drive, OneDrive and Telegram were only exercised against fakes of their APIs | Medium | Medium | Each passes the destination contract against an emulator of the requests the core makes (resumable and session uploads, token refresh and rotation, a sign-in with code and cloud password). Real accounts need the user's own OAuth clients and Telegram app id | Open (E28) |
| Installs from before the rename to Runova (servers, the desktop's own data) reach their updates through the old name | High | Medium | The GitHub repo was renamed, so `SmartClouds/AgentMate` URLs redirect to `SmartClouds/Runova`. Never create a new repo called `SmartClouds/AgentMate`: it would take the redirect over. Each release also publishes the old-named core tarball, and old names live only in the `legacyNames` modules | Open until the compatibility window ends |
| A lost passphrase and recovery key make sealed data unreadable (E48) | High | Medium | Recovery key shown once and required to be saved; reset on runovahq.com deletes only the sealed records and every computer sends its copies again | Open, by design: nobody, Runova included, can open sealed data without the key |
| A sync server that is compromised could rewrite records that are not sealed (E48) | High | Low | Secrets always sealed; "Everything" seals whole records with AAD binding scope, collection, item and key version; a synced host change drops the SSH pin | Open: integrity of unsealed records rests on the server, as for any cloud service |
| Disk Cleanup permanently deletes tens of gigabytes, and a wrong path would delete something that is not a cache (E50) | High | Low | The window sends only ids from the scan the main process holds; every removal is checked against drives, home, protected and project folders, then for staying inside the cache, then for having changed since the scan; a cache folder is layout-checked before it is offered; links are never followed; a folder is renamed before it is deleted; test runs are switched off without a sandbox folder; every removal is logged | Mitigated. Removal is not recoverable by design: a cache is too large for the Recycle Bin. A project pinned to a removed version downloads it again |
| Dependency alerts send each project's package names and versions to runovahq.com in plain text, even for an account whose sync is end-to-end encrypted (E51) | Medium | Medium | Only ecosystem, name, version and the dev flag go up, never a path or a file; the Settings card and the website say so; turning alerts off deletes the account's own package lists, and uploads are refused while it is off | Open, by design: the daily check runs on the server so it works with the app closed |
| A team member can change a shared item that teammates use (E48) | Medium | Medium | Roles (Viewer reads only), team activity for Owners and Admins, key rotation after someone leaves | Open, by design: Members are trusted with what the team shares |
| A forged or replayed payment webhook could give an account a paid type for free (E53) | High | Medium | Stripe events are checked with the endpoint signing secret (5 minute tolerance), NOWPayments IPNs with HMAC-SHA512 over the key-sorted body; every event is acted on once; a crypto payment credits only on `finished` with our own invoice's amount and currency; secrets are sealed and write-only | Mitigated (E53). Only tested against fakes so far |
| A missed Stripe event leaves an account on a type it no longer pays for, or off one it does (E53) | Medium | Low | Stripe retries for days; the subscription events carry the whole state, so any later one corrects it; a card subscription past its period ends three days later without an event | Open: the API has no reconciliation against Stripe's list yet |
| Prepaid crypto plans end silently and online monitors stop (E53, E55) | Medium | Medium | Reminders a week and a day before, in the app, by email and on Telegram; monitors over the limit are paused, never deleted, and their history stays | Mitigated (E53) |
| A stolen node key, or a node that turns hostile, sends false results or connects as another node (E54) | High | Low | The node id comes only from the client certificate the Node CA signed; certificates last 7 days and renew only for the same key; a revoke closes the stream within a second and every gateway refuses the serials; an IP allow list per node; E55 accepts results only for monitors assigned to that node and confirms a problem from another region | Mitigated (E54) |
| The monitoring link exposes RabbitMQ or other internals to the internet (E54) | High | Low | RabbitMQ and PostgreSQL have no published port in any compose file (a test reads them); nodes reach only the gateway's gRPC port; no management plugin, no guest user | Mitigated (E54). One shared RabbitMQ user for the API and the gateway |
| A node is pointed at an internal address and used to probe a private network (SSRF) (E54) | High | Medium | The node resolves a host once, refuses loopback, private, link-local, CGNAT, multicast, metadata and mapped IPv6 forms, and connects to the address it checked; no redirects, 512 KB at most, HTTPS unless allowed; private addresses can be allowed in Development only | Mitigated (E54) |
| Results are lost while the gateway, the broker or the API is down (E54) | Medium | Medium | Results wait in the node's SQLite outbox; the gateway acks a batch only after the API answered for it (a Wolverine publish returns as sent even with the broker down, so it is not used for this); every result has a UUIDv7 id for E55 to store once | Mitigated (E54) |
| A node with a bad network, or a hostile one, raises false outages and wakes a team (E55) | Medium | Medium | Two bad checks in a row on the node, then a second opinion from another node in another region before an incident opens; results count only from the node a monitor is on, for its current definition | Mitigated (E55) |
| A monitor's access key leaks from the server (E55) | High | Low | Sealed with Data Protection; opened only into the definition sent to the node that checks it, over mutual TLS; never in a DTO, a log or the audit | Mitigated (E55) |
| Raw samples fill the database (E55) | Medium | Medium | One row per check with a BRIN index on time; nightly retention by the scope's history days in batches of 10,000; hours and incidents are small and kept | Mitigated (E55) |
| A downgrade quietly stops a team's monitors (E55) | Medium | Medium | Plan enforcement pauses only the newest over the limit, marks them over-limit, keeps their history and tells every member in the app and on Telegram | Mitigated (E55) |
| A monitor's key is sent to Runova Cloud without the person knowing (E56) | High | Low | "Where it runs" asks for consent, naming what is kept, before the first send; the key goes once, over the account's HTTPS, and is never shown again | Mitigated (E56) |
| A monitor is checked twice, on Runova Cloud and on a teammate's computer (E56) | Low | Medium | The run mode syncs with the monitor and every scheduler skips an online one | Mitigated (E56) |
| Someone guesses an unattended-access password (E61) | High | Medium | CPace, so each guess needs a live try on the host; the host waits 1, 2, 4... s and locks password access for 15 min after 10 wrong ones and tells the owner; the server allows 30 password requests per 10 min per computer; 10 characters at least and the common ones refused | Mitigated (E61) |
| The website, or someone who controls it, sits in the middle of a session (E61, E62) | High | Low | The handshake signs both DTLS fingerprints and fresh keys with each computer's identity key; host keys are pinned per ID and a change stops the connection; the relay carries AES-GCM frames it can not read; both sides can compare the safety code | Mitigated (E61). The server still vouches for which account a key belongs to on first contact |
| Someone is watched or controlled without knowing it (E61) | High | Low | Nothing is allowed until the owner turns it on; the request window and the always-on-top host bar say who, and End session works in one click; an OS notification on connect; view only, clipboard and files per session | Mitigated (E61) |
| The relay's traffic costs grow with use (E62) | Medium | Medium | Direct links first; the relay copies one frame at a time each way and ends a session after 12 h or 50 GiB (E67) | Open: the limit is per session, there is no per-plan quota yet |
| The hub and relay state is lost or split across instances (E60, E62) | Medium | Low | Apps reconnect and go online again within seconds after a restart | Open: one API instance while Anywhere is on; a backplane is needed to scale out |
| Control does not work on Wayland or without macOS permissions (E63) | Medium | High | The tab says why and asks for the permissions; the screen can still be seen | Open: the Wayland remote-desktop portal is not used yet |
| The background agent runs as SYSTEM and could be turned against the computer (E64) | High | Low | It accepts only what the owner allowed without asking and runs the same handshake; its token reaches the remote hub only; its config is sealed with DPAPI in a folder only SYSTEM and administrators can open, and its program sits in Program Files; installing and removing it need a UAC prompt | Mitigated (E64). Not yet reviewed by a security specialist |
| The macOS agent depends on `CGDisplayCreateImage`, which Apple has deprecated (E65) | Medium | Medium | The agent reports no screen and turns requests down instead of crashing; ScreenCaptureKit is the replacement if it goes | Open: never run on a real Mac yet |
| Many Linux computers use a Wayland greeter the agent can not see (E65) | Medium | High | The agent turns requests down rather than showing a blank screen, and the help article gives the GDM setting | Open |
| An agent secret leaks from the handover file (E64) | Medium | Low | The file is written for this user only and deleted by the installer at once, or by the app when the install fails | Mitigated (E64) |
